# 策略开发

用户要开发或改进可回测的策略时，先从当前对话、已有研究项目、固定数据与费用资料填写投资委托。调用 strategy_development_plan，把用户原话、项目依据、研究资料和可检验的假设分别注明来源。研究资金和成本可以提出明确的模拟情景。遇到缺字段先查资料或开展能做的工作，仅对会改变硬约束的明确冲突提出具体问题。

从投资委托到通过验证的策略，步骤与产物依赖声明为工作流 `strategy.development`（`workflows/strategy.development.yaml`）。主 Agent 开发或系统性改进一个策略时，用 `workflow_plan` 以该工作流开立计划，可并行的实验/对照步骤并发推进，`workflow_step` 与业务动作同轮合批上报；因子库没有合适的合格因子时，`factors` 步骤可回退到 `sesame/auto-factor-mining:factor.development`。局部诊断或单次对照实验不必建计划。

按投资范围、假设、成本后比较目标和实际执行方式选择 framework、state_machine 或 hybrid。先建立简洁的基线，检查各槽返回的 gaps，再局部替换。需要实际报告时在委派报告作者时明确策略报告目标，传递项目及原生结果固定引用。

普通价格规则无需因子插件。要用因子时先查既有 factor_library，匹配定义、数据频率、用途和开发分区。需要独立因子检验时交给原插件的 factor_evaluate，确实缺定义才安排 factor_search。策略开发负责接入时点、变换、缺值和数值一致性，并用相同开发数据的整套策略对照检验边际贡献。

动手设计或改造前，调用 strategy_development_method 读取与当前判断相符的技法。新想法从 hypothesis-design 推导一种可观察的市场行为和能推翻它的反例。若几种解释都能产生同样的回测图，找最能区分它们的交易证据。根据证据选择方向预测、条件过滤、仓位调节或退出机制，并说明取舍。已有基线时，先用 trade-diagnosis 看成交路径、持仓有利与不利移动、成本和风险集中，再判断哪项改动值得测试。

可把具体的市场机制、替代解释、预期观察和鉴别实验写进 plan 的 research_design。由 Agent 按研究问题填写。在看到基线后形成的新解释随新版本记录。若一种更简单的解释已经足够，可以保留原策略或放弃候选。

研究收盘突破时，可以在编写完整策略前调用 strategy_development_study。用一份开发行情，先定回望期、跟踪期和方向。比较每个突破从信号收盘到下一根开盘的跳空，以及从开盘到指定期限仍能观察到的走势。若机会都集中在入场之前，优先检查报价与可成交时间。开盘后仍有延续时，对照相同时段、波动和风险，再写成本后基线。只有采用同一信号定义的实现才能复用这项判断。

例如“震荡时少亏”可能来自挑中更好机会，也可能仅来自少交易。按 incremental-evaluation 设计交易数或敞口相近的对照，核对被错过的趋势。时点可疑时先检查组件。在固定 SVL 行情的同一事件比较可用输入与不同预热长度。怀疑换手侵蚀时固定预测、风险预算和费率，预先写明改变哪个执行参数、期望成交额或佣金如何变化，再用相同开发期检验。把“机制如预期工作”和“委托目标改善”分别作答，保留退回原版的选择。

用 strategy_development_build 固定 SVL、重放用例和独立的原生实现。用 strategy_development_backtest 预先声明数据、成本、目标、硬约束、参数网格和预算，分批跑完，并检查失败或被约束淘汰的试验。先在开发集对照和择优，再确认冻结的一个候选。保留失败、使用过的留出和真实成交证据。用 strategy_development_compare 比较变体，strategy_development_read 查看诊断和下一步。实盘交易权限应由用户在相应交易流程中单独授予。
