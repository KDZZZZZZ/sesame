# 组件、可用时间与原生验证

修改规则、接入特征或更换目标引擎时，保留策略版本、事件顺序、期望状态、目标数量、费用和可用时间。先用固定输入定位行为差异，再用独立原生实现运行冻结的历史行情。

1. **规则和不变量。** 对正常、延迟、过期和重复事件各写一例。查明平仓后的旧信号能否重新买入，未成交时是否重复发单，数量单位是否一致。记录 SVL 的实际输出与预期。
2. **按需接入因子。** 纯规则策略可以略过这步。确有因子需求时，从已有因子研究插件读取精确定义及开发分区评价。Qlib 的 `SigAnaRecord` 分析预测与标签的 IC、Rank IC 等指标，`PortAnaRecord` 保存组合回测、持仓及风险分析。给策略记录因子的用途、变换、缺值方案和首次可知时间。在同一组时间点核对 Qlib、SVL 或外部输入与原生后端的数值和决策。[Qlib 的记录实现](https://github.com/microsoft/qlib/blob/main/qlib/workflow/record_temp.py)
3. **前视与预热。** 固定在某个决策时刻截断未来数据，比较该时刻以前的特征和信号。再改变指标所见的起始历史，比较同一时刻的数值及实际触发。横截面排名应保留同一时点的完整可交易资产池。记录触发过哪些条件和仍未覆盖的路径。Freqtrade 的切片回测与不同启动长度提供两种独立诊断思路。[前视分析](https://www.freqtrade.io/en/stable/lookahead-analysis/) · [递归指标分析](https://www.freqtrade.io/en/stable/recursive-analysis/)
4. **目标后端。** MT5 路径固定目标能力、翻译、编译和一致性证据，再检查 Tester 的原生回执。Backtrader 路径固定独立 Python 源、数据快照、资金、费率、滑点和引擎版本。用实际订单、成交、净值与回撤回答绩效问题。实现跨引擎等价的结论需要专门的对照证据。

交付时把通过、失败和缺失的结果按组件列出。为缺失项指出哪份输入或哪次运行能解决问题，并保留已通过的独立验证。

**从哪个时刻开始错。** 对单路已收盘行情的固定 SVL 重放，strategy_development_verify 可以在给定事件将每个滚动窗口中过晚收盘或尚未发布的行移除，再看相同时刻的指定节点、状态及订单意图。只截去事件序列尾部仍可能保留窗口内偷看的记录。提供真实的 UTC 决策、开收盘与首次可用时间。没有触发过的逻辑、缺失的发布时间或多路时钟会留下证据缺口。

**区分指标和决策。** 用 warmup_lengths 改变可见历史，从同一初始状态向前运行。数值漂移、信号翻转、订单意图改变分别回答不同的问题。如果 EMA 有轻微漂移但信号不变，先找接近阈值的样本。若状态机换了起点才失去旧持仓，关注状态恢复或初始化。先修复首次分歧的环节，用相同事件复验，然后再衡量成本后绩效。

指定序列节点时会比较整个输出窗口，并保留样本数、摘要和末值。window_history_only 表示序列先前的样本或长度发生变化，而该时刻的节点末值相同。判断预热是否影响交易时，还要看状态和订单意图。未就绪的判断、缺少中间决策、没有缩短历史的对照会标出证据不足。若原始重放使用了自定义起始持仓或状态，需先确定缩短窗口起点的持仓和状态来源。
