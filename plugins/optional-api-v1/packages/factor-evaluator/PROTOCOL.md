# Factor evaluation tool protocol v1

A workflow explicitly selects `{plugin_id, tool, arguments?}`. Neither tool name nor plugin ID is prescribed by the protocol. The implementation must be a trusted installed plugin with a declared capability. Its version/digest is frozen for the run. Calls originate from an active workflow capability or its registered role capability, carrying host provenance; a background service cannot impersonate that invocation.

Every request contains `protocol: "sesame.factor-evaluator/v1"`, `action`, `run_id`. Every successful receipt returns `protocol`, `action`, `runId`, `sessionId` and `receiptDigest`. The digest is SHA-256 of canonical sorted-key JSON of the complete receipt excluding receiptDigest. It detects mismatched/corrupt records; authenticity comes from calling the selected installed implementation, not a model-provided digest.

| Action | Additional request | Required receipt |
| --- | --- | --- |
| prepare | optional dataset_id; options = selected arguments; access = restricted or development-only | inputDigest; data with digest and holdoutMode (workflow-isolated or none); development.rows containing only public development observations; contract.instructions (<=6000 characters), optional candidateExample and dataset/metricColumns metadata |
| candidate | session_id, trial_id, opaque candidate object, accepted_ids | trialId, normalized candidate, candidateDigest, metrics object, eligible boolean, gate text, redundancy array |
| select | session_id, trial_ids | exact trialIds and selectionDigest; freezes the set without returning holdout results |
| finalize | session_id, selection_digest | matching selectionDigest, holdout object, holdoutStatus = evaluated or not-requested, archive.rows plus implementation-specific reproducibility metadata |

The caller workflow owns role arrangement, candidate generation, task order, evidence acquisition and final reporting. It invokes these numerical actions from an authorized workflow capability or registered role capability. The evaluator only requires the data-state dependencies: prepare before candidate/select, and a frozen selection before finalize. Finalize is deterministic computation and does not itself require an Agent. Archived inputs and receipts remain reusable evidence in durable storage; they do not prescribe a report format or a separate research workflow.

An implementation can return `data.inputRefs`, an array of exact published ArtifactRefs consumed during prepare. A caller preserves them as final report dependencies; referenced artifacts retain their own evidence dependencies. These are source identities, not registered dataset IDs. The bundled implementation accepts exactly one of `dataset_id` or `options.inputRef`, where inputRef is a complete fixed `kind:data`, `schemaVersion:1.0.0` reference containing a valid json-rows numeric panel. It verifies manifest/blob identity and the actual bounded bytes, retains input provenance/dependencies, and includes the complete reference in the frozen input digest. It neither registers a host dataset nor converts raw market rows. The existing auto-factor workflow forwards selected evaluator arguments as options, so no new workflow input is needed.

Candidate/session/selection retries are idempotent and immutable. A different candidate under the same trial ID or a changed frozen selection must fail. Failed/incompatible receipts never become metrics. Evaluator implementations own normalization, numerical method, eligibility, redundancy, input immutability and reproducibility; the workflow never computes AST or Rank IC.

A semantic candidate rejection uses EVALUATION_REJECTED, permitting a corrected proposal under the same uncommitted trial ID. Failed attempts retain trialId, attemptIndex, candidateDigest, stage and reason; identical failed retries do not duplicate the ledger. A select failure of an explicit user requirement uses HARD_REQUIREMENT_UNMET, retains lastSelectionReview, and does not freeze a selected set. An interrupted or unknown outcome retains the original pending input for an idempotent retry. Prepare/finalize receipts are bounded to 5MiB; candidate receipts to 64KiB and select receipts to 512KiB.

The bundled implementation requires nested invocation and binds the session to its calling plugin and owning conversation. Subagent calls additionally require a running task from that workflow for the same run. Direct Agent calls, other workflows and other main conversations cannot operate that session. Installed native plugins are trusted code; this is a workflow access boundary, not isolation from malicious native code or external processes.

General research capabilities use development-only access: an evaluator must not ingest or later claim a holdout in that session. The bundled implementation rejects observations after validationEnd. A truly external immutable holdout service may define a future protocol extension; the current workflow does not imply such a guarantee for globally registered datasets.

The bundled implementation supports `options.dataset.mode` = `auto`, `cross-sectional`, or `time-series`. Auto resolves from development symbols only (one symbol => time-series). Temporal metrics are computed separately per symbol and averaged equally, not by pooling asset levels. The numerical model and resolved mode are recorded in the frozen dataset and contract. Cross-sectional AST operators rank/zscore keep their cross-sectional meaning; a temporal task can use causal rolling operators instead.

`options.diagnostics` selects any of `placebo`, `monteCarlo`, `outOfSample`, `walkForward`, `sensitivity`, `regimes`, `bootstrap`, `dsr`, `pbo`. Each value is false, true or the item-specific configuration object described in DIAGNOSTICS.md. Omitted/false items do not run. `metrics.diagnosticPlan` preserves the requested plan; `metrics.diagnostics` retains independent results with status `completed`, `partial`, `not-requested`, `not-applicable`, `unavailable`, `deferred` or `error`. Computation completion is not an overall pass. An inapplicable/unavailable/error diagnostic does not throw away the other metrics, and cancellation still cancels the actual invocation.

Version 1.2 treats legacy `minRankIC`, `minCoverage` and `maxCorrelation` as advisory. Use `options.evaluationPlan = {tests, thresholds, reasons}`: tests overrides options.diagnostics item by item; threshold entries are `{metric,value,operator,mode,source,reason}`. Operators: gte/lte/gt/lt/eq. Only source:user AND mode:required gates, never an Agent preference. A required unavailable metric does not pass. Candidate search requirements defer to select; pairwise constraints resolve on the actual selected pairs (a singleton has no pairwise constraint). Overall validation association, actual return observations, or identified regime/forward-subset association supplies measurable evidence. When overall association is absent but subset evidence is measured, evaluation.status is conditional. Wholly unmeasurable evidence remains ineligible. Keep the normalized plan <=12KB, threshold entries <=8KB and 40 entries; no holdout metric may be used as a selection threshold. If every candidate is unmeasurable the workflow can select `[]` and finalize; the result has no holdout items and `holdoutStatus:not-requested`.

Selected OOS diagnostics expose validation as development evidence and the restricted holdout as deferred before selection. Finalize adds the selected candidate's actual holdout result and finalized OOS metadata. Development-only access has no sealed holdout. Other diagnostics stay in the candidate receipt and are not rerun against holdout by default. Randomized calculations use bounded repetitions, saved seeds, explicit method/sample counts and cooperative cancellation. Large per-symbol details are capped with total and omitted counts; all symbols still contribute to measured aggregates.

For restricted access, the workflow must project research-role context without source inputRefs, options.inputRef or provenance references that expose the full panel. Basic host.resources.read can resolve an exact published reference; hiding holdout rows while disclosing their address does not isolate them. The owning main conversation and durable archive retain the complete source identities. This complements the evaluator's development-only prepare rows and select-before-finalize gate; it is not a claim that published input artifacts are globally private.

## Plan and search receipts in 1.2

prepare.contract includes normalized evaluationPlan and planDigest. candidate.evaluation includes status (measured, conditional, not-evaluable), eligible, measuredEvidence, conditions, invalidations, limitations, evidenceStatus, thresholdResults, hardRequirementFailures, pendingHardRequirements, advisoryFindings and planDigest. Findings carry thresholdIndex pointing to the complete thresholdResults entry; the source, mode and task reason remain inspectable there. These are evidence scopes, not inferred trading rules.

DSR/PBO are deferred in candidate.metrics.diagnostics, which remains immutable. select recomputes the entire registered candidate universe from development-validation returns, including unselected/ineligible candidates. It returns diagnostics.dsr (shared assumptions plus byTrial numeric statistics), diagnostics.pbo (complete-universe CSCV summary), evaluations for selected IDs, redundancy, failedTrials and planDigest. Both search diagnostics record trial IDs, trialSetDigest, periodsByTrial, failed/excluded reasons and returnSource. PBO also records matrixDigest, exact combinations and omitted detail counts. No external/native execution return matrix is accepted through this protocol; it cannot be forged from claimed metrics. An omitted upstream trial is outside observable session scope and remains an explicit limitation.

Failed or missing trial returns, nonsynchronous intervals and undefined Sharpe make the relevant search statistic unavailable. Unavailable advisory evidence can accompany conditional use; an unavailable user required metric blocks selection. A rejected selection does not consume holdout. finalize copies the frozen diagnostics/evaluations and plan unchanged, then computes only selected holdout. No PBO or DSR resampling uses holdout.

All development-subset conditions carry evidenceStatus:exploratory; the candidate carries exploratory-development. A measured subset discovered on the same development data is not independently validated. If an overall association threshold is unmet but measured conditions exist, status may be conditional; eligibility still enforces every user-required threshold. invalidations preserves unavailable subsets and threshold-result references without interpreting negative IC as automatically bad (a task may investigate an inverse relation).
