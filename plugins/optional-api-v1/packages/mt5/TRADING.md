# MT5 manual trading interface

The installed terminal's `mt5_catalog {server:"terminal"}` (or `server:"python"`) is authoritative for tool inputSchema, availability and permissions. Do not guess MCP parameters from Python field names.

Every routed call takes `{server,tool,arguments,command_id}` and optional `save_as`. command_id is a stable 16–128 character `[A-Za-z0-9_-]` ID. Identical requests return saved results; different input/configuration raises conflict. `mt5_command {command_id}` reads the existing receipt without replay. `returned` describes transport, not order acceptance or fill.

| Operation | Terminal tool through mt5_trade | Python equivalent |
| --- | --- | --- |
| Market buy/sell | trade_send_market_order | order_send: TRADE_ACTION_DEAL, BUY/SELL, symbol, volume |
| Pending | trade_send_pending_order; types/expiry follow current inputSchema | TRADE_ACTION_PENDING with native pending type/prices/expiry |
| Modify | trade_modify_sl_tp: SL/TP on a position/pending order; no generic entry-price amendment is inferred | TRADE_ACTION_SLTP or TRADE_ACTION_MODIFY, exact position/order and fields |
| Cancel | trade_delete_order: pending order | TRADE_ACTION_REMOVE with order ticket |
| Close | trade_close_single_position: exact position ticket | Opposite DEAL with exact position, symbol and volume; partial-close rules are native |
| Close-by | trade_close_by_position: two opposite positions | TRADE_ACTION_CLOSE_BY with position/position_by; broker/account must permit |
| Current queries | get_trading_open_positions through mt5_call | orders_get / positions_get through mt5_python; symbol/group/ticket filters |
| History | get_trading_history_orders / get_trading_history_positions through mt5_call | history_orders_get / history_deals_get through mt5_python; timezone-qualified date_from/date_to or supported ticket/position filters |
| Check | Native permissions and receipts | account_info, terminal_info, symbol_info, symbol_info_tick, order_calc_margin, order_check through mt5_python |

**Python order_send routes through mt5_trade**, because trading permission takes precedence. initialize/login also use that route. Ordinary Python reads use mt5_python. Do not switch transport to bypass disabled plugins or permissions. Scripts and EA deployment are separate actions, not a shortcut for unapproved orders.

Python `request` fields are action, magic, order, symbol, volume, price, stoplimit, sl, tp, deviation, type, type_filling, type_time, expiration, comment, position and position_by. Supply only fields appropriate to the action. Quantities are native lots; tickets/magic/position/order use decimal strings. Enums accept documented constant names. Time bounds require timezone-qualified ISO; expiration is UTC seconds. Native prices are binary floats. Keep native retcode/request/order/deal/price/volume; order_check success does not guarantee execution.

## Optional execution_guard (1.3.0)

Python order_send accepts `execution_guard` next to request, consumed only by the Sesame worker. Required fields: observed_at/expires_at (UTC milliseconds; lifetime ≤60s), max_quote_age_ms (1–5000), max_quote_to_send_ms (1–1000), positive decimal price_limit, side, expected_account, expected_server and quote_clock_revision (from the verified quote_clock sidecar).

It supports market/limit and targeted position reduction. Inside the serialized native process it checks account/channel permission, volume bounds/step, target position, verified UTC source time while retaining raw tick.time_msc, quote boundary, order_check, a second fresh tick and expiry before sending once. After order_check it revalidates the exact target position and current account/permissions, then checks source age again inside the monotonic final quote-to-send budget. Preparation after worker queuing is included. Rejection returns `submission_attempted:false`; no send occurs. `execution_timing` reports raw and normalized source/read/send/receipt times and the clock proof separately. The checked request is unchanged after order_check. A bounded quote is not guaranteed market fill/slippage; use limit orders for a native order-price bound. Existing unguarded calls retain their behavior.

The symbol_info_tick result stays raw. The Python envelope adds quote_clock from the actual account/server, using the versioned backend/quote-clock-rules.json table. The FTMO-Demo current-tick rule supports 2026 with documented seasonal offsets; the spring gap, uncertain autumn transition day, unsupported servers and dates remain unverified. Ordinary reads still return raw data; guarded trading requires verified metadata. No offset is fitted from current tick age, and history/copy_ticks UTC request contracts remain unchanged. Broker wall time or reception time cannot replace a verified UTC source time. The independent portfolio-execution plugin measures the model round trip and defaults to M5+; M1 has not been benchmarked.

This package requires Sesame 0.2.3-dev.8+ with live invocation-chain validation. The portfolio-execution helper needs an already configured official Python SDK channel. Its MT5 mapping covers market buy/sell, limit pending orders, exact-position close, pending cancellation and status. Its read-only observation does not install, enable or log in to a terminal. Authorized main-session preparation may enable existing application/algorithmic permissions and initialize the same configured terminal through mt5_trading_prepare; it does not switch accounts. Pure MCP remains available through this package's native tools, but its broker wall timestamps do not establish UTC freshness for the helper. Advanced types and amendments remain the native tools' responsibility.

## Composed workflow execution (1.6.0)

`mt5_trading_context` accepts main conversations and active workflow tasks whose frozen `input.execution` identifies an execution capability and whose `input.tradingPlan` identifies the exact owner, plan and account. The execution context backend is `mt5`; both copies of account and the plan account must match `{accountId,server,revision}`. The workflow plugin name is unrestricted.

`{action:"identity"}` reads configured identity without querying the account. `{action:"snapshot",history_days:7}` requires the configured account's Python IPC and broker connection. It verifies native identity and connectivity before reading positions, orders and bounded history; any failed read, changed configuration or cancellation stops further requests. The snapshot retains raw Python fields and UTC history bounds, so Terminal MCP fields and broker wall time cannot replace it. `mt5_connect` validates Terminal MCP only; `python_installed` establishes neither IPC nor broker connectivity. Python methods and their routes are declared by `mt5_catalog({server:"python"})`; `initialize`/`login` remain permissioned `mt5_trade` operations, not automatic snapshot recovery.

Snapshot failures carry `code`, `message`, and `details` with `transport:"python"`, `requiredTransport:"python"`, `method`, `commandId` and, when available, `commandStatus`, `nativeCode` and `nativeMessage`. Confirmed native `last_error:[-10004,"No IPC connection"]` produces `MT5_PYTHON_UNAVAILABLE`, `retryable:false` and a concrete `recovery`: reconnect the configured Python terminal, verify the same account, then start a new workflow run. Repeating reads in the unchanged environment or reconnecting Terminal MCP does not repair Python IPC. Other failures retain their actual diagnostics without this deterministic classification. Failed reads never become empty positions or partial snapshots; successful `historyCoverage.complete:false` retains the limit of broker-stored history.

Writes through `mt5_trading_order` / `mt5_trading_pause` require executor role and the host's live invocation proof: a tool owned by the task's workflow precedes the exact frozen execution `pluginId/applyTool`, which precedes the native tool. A model-supplied JSON chain, signature or direct delegated native call is insufficient. Account and task/proof validity are checked again after asynchronous preparation. Delegated tasks require the frozen execution contract; the model does not create authorization tokens.

Delegated orders retain mandatory `execution_guard.expected_positions` for the entire symbol, including an explicit empty array for no positions, or the native `cancellation_guard` for one retained order. Main/native permissions, price and freshness protection, unknown-result handling and parent-owned command receipts remain in force. Workflow orchestration cannot widen those execution capabilities.

Python order_send also accepts `cancellation_guard` next to request: exact expected_account, expected_server, symbol, remark, positive decimal order ticket and buy/sell side. It is mutually exclusive with execution_guard and permits only TRADE_ACTION_REMOVE of that exact ticket. With this guard, request must contain exactly two fields: `{"action":"TRADE_ACTION_REMOVE","order":"<ticket>"}`. Do not add symbol, comment, price or other request fields; the symbol and original comment belong in cancellation_guard.symbol and cancellation_guard.remark. Inside the worker, after any queue delay, it verifies the account and permissions, one matching symbol/remark order, ticket, limit type, PLACED/PARTIAL status and remaining volume, then rechecks the account immediately before sending once. It cannot make external terminal account changes atomic with an SDK call.

## Failure and recovery

Inspect transport status, native isError/error and retcode. Accepted order, partial fill, rejection and unknown are distinct. A timeout may happen after acceptance. Keep command_id, read mt5_command, then query real pending orders/positions and bounded historical orders/deals using native IDs and the exact remark. Missing/empty queries do not prove no order. Never change ID/channel to replay an unknown send. Cancellation can race fills and also needs final order/fill evidence.

For an unknown helper order, zero native IDs and balance/credit adjustments are not evidence. Recovery requires positive native IDs, the exact symbol and an actual BUY/SELL deal or uniquely matching active pending order. A recovered pending order can be cancelled after a fresh ownership read and the native cancellation_guard, even if the original command lacked a confirmed ticket. Ambiguous, filled, foreign or changed-account orders are refused. Typed local schema/permission preflight refusals before dispatch explicitly carry submission_attempted:false; transport failures and native Abort/timeout remain unknown.

A settings revision change on the same login/server does not erase or replay an old command. Recovery captures the current revision and checks it throughout the read, with actual native account checks before and after order/deal evidence. A change during those reads rejects the recovery; a stable same-account revision can resolve only from the usual exact evidence. Cancellation uses fresh ownership checks and the same native account guard. The original account/revision remains in the durable record; the verified recovery revision is recorded separately.
