# Reports

把已有文字和数据呈现为统一视觉的报告或回答组件。默认直接 components_show；不熟悉时按需 components_list / components_describe，components_validate 不是必经步骤。

完整报告必须提供 title 标题、lead 开篇回答、highlights 首屏关键结果和 content.sections 正文。lead 用一小段直接回答用户核心问题；highlights 用 1–6 项简短标签和醒目结果展示最重要的数值或定性判断，复用 metrics 的 {label,value,tone?}，结构入口为 report.highlights。顺序为标题、开篇回答、关键结果栏、正文；不另加“摘要”标题。章节按实际问题命名，不编号、不套固定研究模板。target=answer 的独立回答组件不需要报告骨架。

只决定视觉、排版和交付，不选择研究方法或要求固定章节；调查与判断交给 Research 或对应专业能力。正文用 paragraph/markdown，图表只保留必要标题、轴、图例和数据标签，不另造小字说明。

写报告采用“初稿 → 视觉设计 → 组件生成 → 原意与视觉核对”。视觉设计从表达意图出发：逐段明确这段内容要让用户看懂、比较或判断什么，再围绕这个意图尽可能把数据设计成图表，决定取舍、分组、参照、重点、阅读顺序和必要文字。数据关系只帮助落实图型，不作为是否画图的门槛。初稿中的文字、表格、指标和旧图都只是素材，不是要保留的版式。设计过程留在工作中，报告呈现设计后的结果。

承载判断的数据默认由图表表达，不等看到现成序列或表格才画图。想让用户看懂幅度、位置、差异、占比、分布、转折或条件时，把相关数据、基准与关键标注组织到同一视觉中；可以重设计旧图、合并数据、补充标注或新增图，不默认一组数据一张图。highlights 只负责概览，不能替代正文的数据表达。逐段检查仍留在文字或表格中的数据，能用图更直接传达本段意图就入图；数据虽在图中、却看不出要表达的判断，也要重设计。只有精确查数确实更合适时保留表格，必要文字解释发现、原因与意义，不逐项复述数值。不为凑图补造数据，不以图数验收。图型和字段按需查组件目录与 visual-compose。

展望、预测或行动判断中，多个条件导向不同结果时必须用 chart.decision-tree；条件在分支，叶子只放结果，不能用条件表或文字列表代替。单一简单条件可一句话说明；只有事件日期没有分支关系时按时间组织。用户点名的视觉实际使用对应组件。报告或回答中都可用 components_show；target=answer 直接嵌入回复，默认 report。

视觉设计保持初稿的事实、数字、单位、比较口径、关键条件、时间范围、证据和结论含义。重新生成、改版或使用新版组件时，重新设计信息层级、章节、图型和文字分工；旧章节数、图表数和段落不是默认约束，委派时不得自行把它们锁死。修复具体报错才只调整受影响部分。使用受控组件、固定数据和宿主发布链，修订沿用原报告及精确修订，不提交自由 HTML/CSS/JS。

发布前逐段对照表达意图：该让用户看懂的内容是否已通过图形清楚传达，仍在文字或表格中的数据是否还可以入图，首屏、证据图和条件树是否易读且原意未变；有图或渲染通过不能替代这一步。发布后核对当前修订的 report_check；导出另行确认。详细步骤见 visual-compose 与 report-delivery。
