name: report-writing
description: 把分析结果写成有用、可核对的结论：先回答问题，再给关键证据与下一步，必要边界贴近对应判断；编写报告文字时使用。
---

读者需要先知道三件事：结论是什么、有什么依据、下一步观察或行动什么。把已登记数据转成可核对的判断，不复述分析过程。默认沿用 report-design 的 outline，使主结论与证据易于扫描；需要其他论证结构时可扩展，不以固定字段限制表达。

正文保留结论、关键证据和必要表格。完整原始 JSON、大结果和执行回执保留为可追溯的固定数据引用或证据附件，在 `method.sources` 中标明对应来源；同一份完整回执不在多个章节重复嵌入。读者应能沿引用核对全部细节；数据引用不代替报告本身的编写与发布。

每句话都要提供结论、依据、关键数字、判断条件或下一步。正文、图注、元信息、节点说明和折叠区一起精简：删除模板化免责声明、泛泛适用范围、无意义的否定和自我辩护，无用文字直接删除。必要边界写成具体事实、对当前判断的影响或还需观察什么，保留真实来源与条件，不用空泛套话代替信息。

## 每个字段写什么

- `verdict.headline`：对象 + 结果 + 程度或比较 + 口径，一句话只有一个判断。
  - 好：「验证期净亏损 9.49 USD（−0.09%）。」
  - 差：「本研究在严格冻结的流程下经过训练、选择与独立验证后，结果显示策略表现……」
- `verdict.detail`：可选，补充关键依据或影响结论使用的一项边界，不为填字段强加限制。
- `section.title`：名词短语，说明这一节回答什么（训练与验证、亏损构成）。
- `section.takeaway`：读这一节图表应得出的结论，句中出现图上能看到的比较。不写「下图展示了……」。
- `finding.claim`：一个可以被数据核对的判断。`evidence` 用结构化数值 `[{label, value, format, unit}]`，不要把一串数字揉进长句。`caveat` 仅在会改变该判断或行动时补一句具体边界。
- `metric.label`：简短的名词（净利润、最大回撤、有效样本）；`hint` 只写口径（原生统计、共 14 条）。
- `method.steps` 写需要追溯的口径（选择规则、清洗）；`method.limits` 只保留有用且未在正文解释的边界；`method.sources` 放来源、ID、哈希、版本与文件名。方法区默认折叠，空项省略。

## 数字

- 每个数字都来自 `reportKit.rows` / `window.report.readData` 的结果，用 `reportKit.format` 或字段的 `format` 格式化；不手写、不先四舍五入再计算。
- 带单位和比较对象：「比 B 组高 2.17」，而不是「较高」；区分收益率与百分点差。
- 同一指标全文同名、同精度、同单位，以第一次出现的名称为准（净利润 ≠ 盈亏 ≠ 收益）。
- 关键统计旁给出交易数或观测数。样本不足确实影响比较时，说明具体影响和下一步验证；已有不确定性估计就展示，不为所有小样本统一追加免责声明。

## 语言

- 先结论后依据；一句一事；主动语态；用具体动词（亏损、高于、过期、排除）。
- 正文不出现代码标识符、函数名、字段名、文件路径、哈希、ID 或 JSON；需要追溯时放进 `method.sources`。用读者的名称：「Lookback 16」而不是「InpLookback=16」。
- 同一边界只写一次：影响结论或行动的贴近相应判断，追溯细节放折叠方法区；折叠区也只放有用信息，不把已删的套话搬过去。
- 默认不单列“时效与覆盖”“数据质量”“研究局限”等检查性章节。数据截止与时区放元信息；业务触发、失效条件留在情景或决策树。来源报错、权限、凭据缺失等过程信息不占正文，必要核验记录放折叠方法区。用户要求数据审计或这些问题本身改变决策时，再解释实际影响。
- 不写过程叙事（首先、然后、经过核验）、工具调用与修复经历，也不写「本页」「下方」这类指引。
- 不确定时直接给事实与下一步：「每组 1 笔交易；继续积累同口径样本后比较参数」，而不是「可能存在一定局限」。没有安排自动执行时，下一步写成建议或待观察项。
- 语言跟随任务：中文任务写中文，界面需要双语时自行提供本地标签，通过 document.lang 选择。

## 原版结构起点

以下章节按任务取舍，不为凑模板增加无用内容。

Research：

1. verdict：核心问题的答案。
2. metrics：样本量，加 2–4 个直接回答问题的数字。
3. sections：主要发现（趋势或对比图）→ 影响判断的驱动或比较（bar / heatmap）→ 下一步与条件情景；按实际问题取舍，不为凑章节加入质量、覆盖或核验汇报。
4. method：需要追溯的清洗规则、统计口径和来源，默认折叠。

Strategy（先读 [backtest.md](backtest.md)，其中四项必备内容不能省略；以下是可扩展的论证顺序）：

1. verdict：验证期（或样本外）结果，以及是否支持策略假设。
2. metrics：验证净利润、收益率、最大回撤、交易数、选中参数。
3. sections（3–5）：训练与验证（hbar，signed）→ 参数敏感性（heatmap 或 bar）→ 信号或规则漏斗（bar）→ 损益构成（hbar，signed）→ 逐笔证据（固定 run/result/trade 数据，可筛选或下钻）。
4. method：选择规则、冻结方式、建模方式、限制、构建与任务 ID。

## 发布前自检

- 只读 verdict 和各节 takeaway，能否复述完整论证？
- 每个 takeaway 是否有可检查的证据支撑？每个数字能否在 rows 或其登记计算中找到？
- 首屏是否没有代码、ID 和过程叙述？每条限制是否只出现一次？
- 每个正文章节能否回答用户的实际问题或改变下一步？无用章节直接删除，必要边界并入对应判断。
- 删掉一句话后，用户是否会少知道一个事实、依据、判断条件或下一步？如果不会，就删掉；图注、元信息、节点说明和折叠区同样检查。

## 补充：让图形同时保留证据

延续原版结论语言，只吸收 Lieflat 值得借鉴的读图方法：先让读者一眼看到比较，再允许逐点查看原值；计数适合真实单位点阵，连续价格不应被画成没有明确单位的装饰圆点。图例、直接标注、缺失说明和控件都服务于问题，不把演示组件数量当作报告质量。

价格、金额与票据的精确字符串保留到表格和提示，不通过 Number 重新计算金融统计。所需统计由已登记计算结果提供，来源可追溯。完整 ArtifactRef、revision、digest 和引擎细节放进来源区；主文写用户理解的范围与口径。
